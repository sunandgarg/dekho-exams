# AI Trove Spring & Spring Boot source kit

Original educational sources for the separate Spring subject. Baseline: JDK 21, Maven 3.6.3 or later, Spring Boot 4.0.8 and its managed dependencies. This is a pinned learning baseline, not a claim to use the latest release.

KafkaBoundaryContractTest adds eight broker-free checks against Spring Kafka 4.0.7 API types: manual-ack listener metadata and factory setting, a stock debit committed with its event marker, safe identical replay, rejected conflicting replay, rollback without acknowledgement, key/payload mismatch, producer key arguments and visible send-future failure. Spring Kafka is a managed dependency of the source kit; ReceiptApplication does not start a listener, publish records or configure serializers. These tests do not establish broker acceptance, offset commits, rebalance behavior, dead-letter publication or end-to-end relay recovery. A disposable-broker suite and target-database tests remain required before making delivery guarantees.

GraphQlBoundaryContractTest adds eight direct schema-execution checks with Spring GraphQL 2.0.5: selected fields, tenant-scoped reads and lists, list bounds, non-null error propagation, a versioned mutation, stale-version rejection and cross-tenant mutation denial. It uses an in-memory ledger and a test-supplied tenant context. ReceiptApplication does not register this schema or expose a GraphQL endpoint. These checks do not prove authentication, HTTP behavior, persisted concurrency, nested resolver authorization or a deployed query-cost limit.

The nested `reactive-r2dbc` Maven project has a separate dependency graph. Run `mvn test` from that directory after testing the main kit. Its six R2DBC checks use Boot 4.0.8-managed R2DBC H2 and H2 2.4.240: subscription timing, bound values, a committed event marker and debit, rejected debit rollback, stale version and wrong-tenant rollback. The main JDBC teaching project pins H2 2.3.232; combining both H2 versions in one test classpath caused an API linkage failure, so the reactive fixture stays isolated. Neither project tests a production database, pool, deployed WebFlux endpoint or JDBC/R2DBC cross-transaction behavior.

The nested `batch-chunks` Maven project uses Spring Batch 6.0.5 and Boot 4.0.8 with `spring-boot-starter-batch-jdbc`. The JDBC starter matters: a file-backed business `DataSource` alongside Boot's in-memory Batch repository does not persist job history. `BatchBoundaryContractTest` has two in-process checks. A four-row receipt import uses chunks of two; an injected failure in the second chunk leaves the first two rows committed. A restart with the same identifying job parameter completes with a key-based H2 writer, and rerunning a completed instance is rejected. The saved cursor reports two reads after the first failure, but the local restart can revisit earlier rows, so the writer must tolerate replay.

`TwoProcessRestartContractTest` now has three checks against file-backed H2 and persisted Batch metadata. One starts separate JVMs after a recorded `FAILED` execution and checks one `BATCH_JOB_INSTANCE` row, two `BATCH_JOB_EXECUTION` rows and four distinct target IDs. One forcibly kills a child worker after its first chunk commits: the repository remains `STARTED`, a same-manifest launch is blocked, and `JobOperator.recover` is called only after the test confirms the old process is dead. The recovered launch completes under the same instance. A third check changes a source row after a failed execution and confirms the stored digest rejects the restart before a second Batch execution is created. These are H2 boundaries. They do not prove a crash during a commit, distributed worker fencing, immutable source isolation during an active read, broker side effects, or target-database behavior.

`BatchFaultPolicyContractTest` adds three checks in the same isolated project. One invalid row consumes the configured skip budget while a temporary processor failure recovers on retry; a second invalid row makes the job fail after an earlier commit; an always-failing temporary exception exhausts its retry budget and leaves its chunk uncommitted. A `SkipListener` records the skipped source ID and reason in an H2 quarantine table using a stable key. The tests do not classify production database errors, implement a full per-manifest reconciliation ledger or correction workflow, or prove remote side-effect safety.

The nested `modulith-boundaries` Maven project uses Spring Modulith 2.0.8 and Boot 4.0.8. Two architecture tests accept a dispatch module's dependency on the inventory root API and reject a dependency into its `internal` package. Those two checks verify the classpath structure; they do not start an application context.

`InventoryModuleIntegrationTest` adds two module-sliced Spring context checks. InventoryReservation starts while the neighboring dispatch bean is absent; a valid 19-unit reservation emits one matching ReceiptReserved event and an invalid 59-unit request emits none. The fixture uses an in-memory map. It does not test a database transaction, publication registry, asynchronous listener, process restart or broker delivery.

Run `mvn test`, then `mvn package`, then `java -jar target/spring-learning-kit-1.0.0.jar --server.address=127.0.0.1 --server.port=8080`. Maven downloads third-party dependencies under their own licences. The ZIP includes sources and declarations only, not dependencies, JDKs, compiled output or private configuration.

ReceiptApplication is the HTTP entrypoint. Other main classes are standalone teaching fixtures. The API uses an in-memory ReceiptStore and loses receipts on restart. JdbcReceiptLedger is a separate H2 transaction fixture; it is not the API repository. DriverManagerDataSource is not a connection pool. This kit is not a deployable payment service or production identity system.

Public health: GET /actuator/health. Protected API: GET /api/receipts and /api/receipts/{id}; POST /api/receipts accepts JSON with a positive amountMinor. ReceiptSecurity contains clearly labelled local-fixture Basic credentials, solely for reproducible loopback tests. Never deploy that user store or password. CSRF remains enabled; an authenticated-looking Basic header alone does not make POST valid. Security tests check established users with and without CSRF separately. No token-fetch/login UI is supplied.

Additional contracts use Spring Data JPA, WebFlux and OAuth2 resource-server/Jose libraries managed by the pinned parent. The event controller is a mock-tested contract outside the HTTP entrypoint component scan; it is not an exposed production SSE service. Temporary RSA test keys validate bearer trust without a remote authorization server. Boot import registration is present in the source-kit resource; no separately published starter is supplied.

Tests cover direct construction, singleton/prototype identity, request- and session-scoped proxy dispatch, missing request context, qualifiers, cleanup, local events, self-invocation, effective property overrides and startup validation, conditional assembly, cache ownership, JPA lifecycle/lazy-query counts/optimistic locking, transaction propagation/event phases and checked-exception rollback rules, method authorization including one tenant-specific read and one tenant-specific write, bounded meter identities, derived repository queries/projections/keyset reads, auto-configuration registration/back-off, local JWT signature/claim/scope validation, cache eviction, Reactor demand/cancellation and mock WebFlux SSE, JSON validation/errors, conditional ETag GET and If-Match write responses, local idempotency-key replay and conflict decisions, media-type 415/406 decisions, nested body validation, page bounds, local rollback, H2 receipt/outbox atomicity and guarded claim state, a local dependency health indicator, real HTTP health/authentication/CORS and CSRF filter behavior. The If-Match and idempotency fixtures use one synchronized in-memory controller each; neither proves atomic writes across instances or a persistent database. The outbox fixture checks one H2 transaction and sequential claim, not crash recovery or broker delivery. Tests do not prove production-database isolation, durable queues, distributed caching or deployment-level drain behavior.

The next boundary fixtures check an H2 nested savepoint, object versus direct-parameter MVC validation, one public ProblemDetail shape, a failed @Async future, a same-key local synchronized cache load, and the default role-authority prefix. The cache test uses ConcurrentMapCacheManager in one process. The MVC tests use standalone MockMvc with explicit validator/advice registration. These fixtures do not establish target-database savepoint support, a deployed filter chain, distributed cache locking, a configured production executor or remote identity claims.

Worker recovery fixtures add a one-thread, one-slot executor rejection; an H2 outbox lease with expiry and token-checked acknowledgement; and an H2 event-ID ledger committed with a stock mutation. A separate rejected mutation confirms that the event ID rolls back with it. These are local, independent tests. They do not assemble an HTTP-to-broker relay, prove concurrent claims across nodes, check a target database, or provide restart-safe work by themselves.

The tenant JWT boundary fixture adds a local Spring web context with a signed token, required tenant_id claim, receipt.read scope, method-security proxy and tenant-scoped H2 query. It checks an accepted east-tenant read, wrong scope and cross-tenant 403 responses, missing-claim 401, spoofed X-Tenant headers and distinct rows sharing one receipt ID. The fixture is separate from ReceiptApplication and does not install a real issuer, JWKS rotation, tenant membership registry or database row-level security. The runnable API still uses the local Basic fixture described above.

TenantReceiptCommandFlowTest adds a separate combined local write context. Its stateless bearer POST requires receipt.write, checks the validated tenant principal at a managed service, updates a versioned H2 row with a tenant predicate, and commits an outbox row plus a tenant-scoped replay record in one transaction. Eight tests check acceptance, unchanged replay, conflicting key reuse, stale version, wrong tenant and scope, missing tenant claim, and rollback after an injected failure. The test disables CSRF only for its stateless bearer configuration; ReceiptApplication retains Basic credentials and CSRF. Requests are sequential, keys are local, H2 is in memory, and no relay or broker runs. This test does not turn ReceiptApplication into a durable or production-authenticated API.

MultipartReceiptImportTest uses standalone MockMvc and a JUnit temporary directory. Five tests check a short accepted CSV under a generated filename, oversized input, fake CSV media type, malformed UTF-8, empty and missing parts, and absence of stored files on rejection. The controller is not registered in ReceiptApplication. MockMultipartFile does not prove servlet or proxy upload limits, durable storage, complete CSV parsing or access control. The fixture's 128-byte cap is a test boundary, not a recommended production limit.

ReadinessHealthGroupHttpTest starts ReceiptApplication on a random local port with probes enabled and a test-only importStore indicator. The group returns 503 when that indicator is DOWN while liveness remains 200 and anonymous API access stays 401. ReceiptSecurity permits `/actuator/health` and its nested health paths; other routes still require authentication. The indicator is not a real dependency, and this test does not configure a deployment orchestrator or run a graceful-drain scenario.

OutboxRelayFlowTest adds seven deterministic H2 checks across a producer commit, sequential claim, consumer event-ID reservation, token-fenced acknowledgement, due-time retries and a parked dead state. It uses a logical clock and direct method calls, not a scheduler or broker. Producer and consumer transactions are separate. The model does not prove concurrent claims on a target database, external publication, process-crash recovery or exactly-once delivery. Add those integration checks before deploying a worker.

ScheduledOutboxPollerTest adds four more local checks with a real ThreadPoolTaskScheduler: a background poll, fake transport failure and retry, a two-row batch cap, and duplicate-safe completion after a lost acknowledgement. The scheduler is created only inside tests and uses H2 plus a callback in place of a broker. The runnable ReceiptApplication still has no scheduled relay. Target-database races, restart recovery, broker confirmation, in-flight shutdown and deployed metrics remain untested.

ConcurrentOutboxLeaseTest adds a two-thread, two-connection H2 claim race and a logical-time token-checked lease renewal test. A single conditional UPDATE wins the local race; renewal rejects a stale token, an expired lease and a shorter deadline. These tests still do not prove behavior on the production database or fence an external publish.

BootRelaySettingsTest starts a non-web Spring Boot context to check command-line batch-size override, explicit Duration units and startup rejection of an invalid effective value. It also loads a real temporary application.properties file, checks a file/CLI collision and profile-specific override, and distinguishes required from optional missing imports. RelaySettingsProcessTest runs twelve checks in a separate child JVM: inherited RELAY_BATCHSIZE and RELAY_TIMEOUT values, CLI precedence, invalid environment input, one- and two-hop relative imports and missing required imports, local configtree file binding, environment override of a tree value, missing-tree and invalid-tree failures, and an extensionless properties file with a format hint. The probe prints only non-secret values. The file tree is made inside a test temporary directory; these tests do not load a production deployment mount, access a real secret source or start ReceiptApplication.

SchemaEvolutionContractTest uses direct H2 SQL to check nullable expansion, old-writer compatibility, a local backfill and a NOT NULL contract that rejects the old insert shape. FlywayReceiptMigrationTest separately applies three ordered SQL files under src/test/resources/db/relay-migration to H2 2.3.232 with a test-scoped Flyway starter. It checks migration history, repeat execution, a checksum mismatch, old-writer success at V2 and rejection at V3. BootFlywayStartupTest checks a separate non-web Boot context: V2 and V3 are applied before reading rows, while damaged history prevents the next startup. Its unique H2 URL is passed as a command-line property because the packaged datasource URL outranks a builder default. ReceiptApplication does not run Flyway at startup. These fixtures do not prove target-database DDL locks, a concurrent replica rollout, a large-table backfill or crash recovery.

RestClientBoundaryTest uses an explicit SimpleClientHttpRequestFactory against a random-port loopback HTTP server. Four tests check a returned body, one attempt for a 503 response, a read timeout after the server accepts a request, and a POST that changes server state before its response times out. Replaying the same key yields two requests but one modeled write because the local handler enforces an in-memory key set. This does not prove TLS, proxy or alternate-factory behavior, a production upstream, durable key storage or concurrent first-use safety.

WiringAndBindingContractTest adds four local checks: a primary gateway with one qualified fallback, the identity change caused by direct @Bean calls with proxyBeanMethods=false, @Order on an injected list, and an MVC form binder that ignores a submitted privilege field. JdbcParametersAndKeysContractTest adds two H2 checks: a named ID collection kept inside a tenant-scoped SQL predicate and a database-generated insert key. These fixtures do not prove a production database driver, deployed servlet filters, remote gateway availability or authorization beyond the stated local binding test.

LifecycleAndMvcDispatchContractTest adds eight checks. It compares lazy bean creation with an eager consumer, verifies a lazy target plus injection proxy, records @DependsOn initialization and reverse destruction, selects MVC handlers through a format query parameter, checks local exception-handler precedence and scoped advice, reads typed and raw Boot runner arguments in order, and confirms a failing runner prevents successful startup. The first lazy-injection check intentionally failed when the target bean remained eager; the corrected fixture marks the target lazy too. These local contexts and standalone MockMvc calls do not prove deployed traffic admission, cross-replica lifecycle ordering, production advice registration or platform shutdown behavior.

For one standalone main, run `mvn dependency:build-classpath -Dmdep.outputFile=target/classpath.txt`, then use target/classes plus that dependency classpath with `java -cp ... in.aitrove.learning.ContainerContracts`. Exact verified output is in the editorial handoff. No preview flags are required.
